# v0.48.0 - 2026-11-11

> 🗜️ **压缩从「三个图事件 + 一个子插件」收回成「一个节点 + 一段区间」**。旧的 `context_compactor` 用「守卫算 token → `Goto` 分岔 → 压缩节点 → 回到轮开始」三跳来实现压缩，代价是拓扑里凭空多出三个只有压缩知道怎么走的中间站，而判阈值与真压缩本来是同一次决策的两半。这一版把三个事件、它们的默认跳转、以及整个 `context_compactor` 子插件一起删掉，压缩变成 `base_nodes` 里挂在 `ON_BEFORE_REQUEST` 的 `HIGH` 档节点：先看总量过不过门槛，过了就用 `get_compaction_range` 求出**一段可以安全丢弃并概括的闭区间**，只压这一段，区间外的原文原样拼回。

## Added

- `core/compact/`（新包，16 个模块）：压缩器本体从研究包迁入主包，与图无关、可独立调用 ——
  - `compact.py` 的 `compact_now(messages, client, retain_tokens, *, max_characters=2000)`：`ChatHistory.from_messages(messages).to_history()` → 逐段 `truncate_content_if_need` → 拼成 `"\n\n".join(...)` 后连同 `COMPACT_PROMPT` 一起请求模型 → `TokenPruner.prune(retain_tokens)` → 返回 `CompactSuccess` / `CompactFailed`；
  - `chat_history.py` 的 `ChatHistory`：纯容器，把 `BaseMessage` 列表渲染成带 `[User]` / `[Assistant]` / `[Assistant tool call]` / `[ToolResult]` 标签的行，**不解析平台消息段、不带渠道知识**；`SystemMessage` 不参与渲染；
  - `token_pruner.py` 的 `TokenPruner`：按 `retain_tokens` 从尾部保留；
  - `consts/`：`labels.py`（`TRUNCATED_LABEL` 存字符串、`TRUNCATED_TEMPLATE` 存 `Template`、`TOOL_CALL_LABEL = "$name($args)"`）、`prompt.py`（`COMPACT_PROMPT`，三块输出 + 四态 + 长度目标）、`tags.py`（`SUMMARY_TAG = "summary"`）；
  - `runtimes/`：`CompactSuccess`（`summary` / `used_time` / `tokens_before` / `tokens_after` / `messages_before` / `messages_after`）、`CompactFailed`（`reason` + 可选 `exception`）。
  - `utils/`：`base_calculate`（`int(len(content) * 0.47)`，`AIMessage` 额外拼 `tool_calls`）、`extract_content`、`extract_tool_calls`、`truncate_content_if_need`。
- `plugins/base_nodes/nodes/compact.py` 的 `compact_if_need`：挂在 `ON_BEFORE_REQUEST`，`priority=HIGH`。门槛判据是 `sum(base_calculate(message) for message in messages) < context_window - max_tokens`，过门槛才求区间、才发请求。
- `plugins/base_nodes/utils/get_compaction_range.py` 的 `get_compaction_range(messages) -> Optional[Tuple[int, int]]`：只求区间，不碰模型、不碰 token 预算 ——
  - 右端 = **最后一段连续 `HumanMessage` 的起点 − 1**，与列表尾部挂什么无关（什么都没有 / `AI(tool_calls)` + `Tool` 轮 / 普通 `AI` 回复都一视同仁）。群聊里用户连发的几十条原话是一个整体，必须完整留在区间外；
  - 左端 = 最后一个 `SystemMessage` 之后（系统提示词不进压缩器）；
  - 起点跳过 `ToolMessage`、终点回退带 `tool_calls` 的 `AIMessage`（不拆工具组、不留孤儿工具结果）；
  - 可用长度不足两条时返回 `None`。
- `core/compact` 的 9 个符号经 `core` 转出：`ChatHistory` / `TokenPruner` / `compact_now` / `CompactSuccess` / `CompactFailed` / `base_calculate` / `extract_content` / `extract_tool_calls` / `truncate_content_if_need`。

## Changed

- **压缩的挂载点**：`ON_BEFORE_COMPACT` / `ON_COMPACT` / `ON_AFTER_COMPACT` 三个事件上的 handler → `ON_BEFORE_REQUEST` 上的 `compact_if_need`（`HIGH`(100)，是这个事件里跑得最早的处理器，早于 `time_inject`(2) / `build_prompt`(1) / `pick_tools`(1)）。
- **压缩结果写回的方式**：`Overwrite([摘要, *保留窗口])` 整表替换 → `Overwrite([*messages[:p_start], HumanMessage(摘要), *result.messages_after, *messages[p_end + 1:]])` —— 区间外的原文（系统提示词、当前这轮用户原话、后续工具轮）不再经过压缩器，也不再被重建。
- **摘要的标签**：`<abstract>` → `<summary>`（`SUMMARY_TAG`），压缩提示词里对上一轮存档的读取说明同步改为「被 `<abstract>` 或 `<summary>` 包裹的段落」—— 旧会话里残留的 `<abstract>` 摘要仍按机器存档处理。
- `plugins/default_routing/nodes/on_turn_start.py`：下一跳 `ON_BEFORE_COMPACT` → `ON_BEFORE_REQUEST`。
- `plugins/base_nodes/main.py`：新增 `registry.on(ON_BEFORE_REQUEST, compact_if_need, priority=HIGH)`，导入补 `HIGH` / `ON_BEFORE_REQUEST` / `compact_if_need`。
- `plugins/base_nodes/nodes/call_llm.py`：注释里「压缩后的摘要已由 `context_compactor` 写进 messages」→「由压缩节点自己写进 messages」。

## Removed

- **`plugins/context_compactor/`（整个子插件，22 个文件）**：`main.py` / `metadata.toml` / `README.md` / `config.example.yaml` / `consts/` / `models/` / `nodes/` / `utils/`。守卫 `should_compact`、压缩 `compact`、`calculate.mode` / `keep_count` / `prompt_file` / `recall_system_prompt` 这些配置键一并消失。
- **三个压缩事件**：`consts/graph_events.py` 里的 `ON_BEFORE_COMPACT` / `ON_COMPACT` / `ON_AFTER_COMPACT` 常量与 `GRAPH_EVENTS` 里的对应条目，`consts/__init__.py` 的导入与 `__all__` 同步删除。`GRAPH_EVENTS` 由 11 个变 8 个。
- **`plugins/default_routing/nodes/on_before_compact.py` / `on_compact.py` / `on_after_compact.py`**：三个默认跳转节点连同 `nodes/__init__.py` 的导出、`main.py` 的三行注册一起删除。`default_routing` 的节点文件由 11 个变 8 个。
- `plugins/base_nodes/nodes/compact.py` 里旧的切点算法（`is_droppable` / `find_cut_point` / `find_last_not_HumanMessage_index` 及其在多轮迭代中产生的变体）：切点职责整体上移到 `get_compaction_range`。

## Fixed

- **「一整组用户原话」会被压掉**：旧算法以列表尾部为准数连续 `HumanMessage`，尾部一旦是 `ToolMessage` 或普通 `AIMessage`（工具轮跑完、或助手刚回完话），计数归零、保护失效，群聊里连发的几十条原话整组进了压缩区间。新算法从后往前找**最后一条 `HumanMessage`** 再向前扩到该组起点，与尾部形态无关。
- **`SystemMessage` 会被送进压缩器**：旧算法只保证它不被当作切点，但它仍可能落在区间内部，而 `ChatHistory` 渲染时会丢掉 `SystemMessage` —— 压缩后同一份系统提示词既没进摘要、又从区间里消失。新区间的左端强制从最后一个 `SystemMessage` 之后起算。
- **索引 0 被误判为空**：旧写法 `if not p_start` 把合法的 `0` 当成 `None`。新的 `get_compaction_range` 用显式 `is None` 判空。
- **切点相等时抛异常**：`p_start == p_end` 是合法状态（区间里只有一条消息），旧实现 `raise`，异常被 `_dispatch` 吞掉后表现为「静默不压缩」。新实现返回 `None`。
- **门槛与区间互不感知导致的无意义请求**：旧守卫挂在独立事件上，只要总量过门槛就 `Goto` 进压缩环节，压缩节点再自己决定区间。现在门槛与区间在同一次调用里判断，区间为空时不会白发一次模型请求。

## Note

- **破坏性**：`context_compactor` 子插件与三个压缩事件删除后，任何引用 `ON_BEFORE_COMPACT` / `ON_COMPACT` / `ON_AFTER_COMPACT` 或 `context_compactor` 子插件的部署侧配置（`sub_plugin` 下的启用项、`plugin_configs` 里的 `context_compactor` 段）都会失效；压缩改为默认随 `base_nodes` 一起启用，没有独立开关。
- **`retain_tokens` 仍是硬编码 `20000`**：`TokenPruner` 按这个数从区间尾部保留，配置入口尚未设计。区间正文不足该数时一行都不删，而摘要照样插入 —— 区间很小、总量却过门槛的场景会净增 token（实测 5,864 token 的区间得到 +5.6%）。
- **门槛只看总量，不看区间**：触发条件由整段历史的 token 数决定，真正被压的是 `get_compaction_range` 给的区间，两者大小无关。区间本身超过 `context_window` 时压完仍可能超限，等下一轮再压。
- **压缩不再重置轮次**：旧实现压完跳回 `ON_TURN_START` 重走一轮（`build_client` / `pick_tools` 全部重跑），现在压缩发生在 `ON_BEFORE_REQUEST` 内部，`ON_TURN_START` 的阶段已经过完，压完直接往下走到 `ON_REQUEST`。
- 实测（`ginka-1` / `ginka-2` 的 `deepseek-v4.1-flash`，12 路并发 + 3 轮链式）：12/12 成功，总耗时 22.0s，合计 371,712 → 250,327 tokens（-32.7%），单例节省 10,036~10,197 tokens，结构检查 48/48 通过（`SystemMessage` 唯一位于 0 / 无孤儿 `ToolMessage` / `tool_calls` 结果齐全 / 摘要唯一 / 尾部用户原话组连续）；链式 3 轮输出稳定在 ~20.7k tokens，摘要始终只有一条，第一轮摘要里的事实第 2 轮起全部带过来。
