# v0.23.1 - 2026-10-20

> 🧱 **移除压缩守卫，修掉它防御过度的问题**。守卫的判据与实际 token 用量无关，压缩产物一旦写进消息头部就会被反复命中。

0.23.0 把守卫判据从 `messages[-1]` 改成「过滤 `SystemMessage` 后的首条」，位置算对了，但**判据本身是防御过度**：只要首条带 `<abstract>` 标签就 `Abort`，完全不看当前 token 用量。而摘要由 `compact` 写进 `messages` 后会长期留在头部，于是压缩之后的流程会再次撞上这道拦截，与「是否真的还需要再压一次」没有关系。

判断是否需要压缩本来就有明确的量化依据 —— `usage_tokens + max_tokens < context_window`。守卫想防的「二次压缩」，只有在压缩后 token 仍然超限时才成立，用「摘要存在」当代理条件既不准也不必要。本版直接把守卫段删掉，压缩与否只由 token 计算决定。

删掉守卫也就没有「已压缩过就拦住」的兜底了：如果压缩后的结果依然超出上限，流程会再次进入 `compact` 再压一次。这条路径留给 token 计算本身兜底。

同时把 `config.example.yaml` 的 `keep_count` 默认值从 5 提到 20。压缩后的上下文里，摘要约 3200 字符、`SystemMessage` 约 2800 字符，`keep_count=5` 只保留约 1000 字符真实语料 —— 摘要体积是保留消息的 3.2 倍。摘要用第三人称客观叙述，与提示词要求的人设口吻相反，权重压在摘要上会让压缩后的说话风格明显漂移。提到 20 后保留约 4800 字符、11 条 AI 消息，比例反转到 0.7 倍，压缩后上下文总量约 6300 token，占 128K 窗口的 5%。

## Changed

- `config.example.yaml`：`compact.keep_count` 默认值 5 → 20，注释补「`ToolMessage` 不计数」。
- `nodes/should_compact.py`：块内导入对齐按删除后的最长前缀重算。

## Removed

- `nodes/should_compact.py`：删除「摘要存在即 `Abort`」的守卫段。该判据与 token 用量无关，压缩产物留在消息头部后会被反复命中。
- `nodes/should_compact.py`：删除随之失效的 `Abort` / `HumanMessage` / `SystemMessage` / `ABSTRACT_TAG` 四个导入，以及空的 `langchain_core.messages` 导入行。

## Fixed

- `nodes/should_compact.py`：守卫防御过度 —— 把「摘要出现在首条」当作「需要二次压缩」的充分条件，导致压缩后的流程被拦断。判断压缩需求现在只由 `usage_tokens + max_tokens < context_window` 决定。

## Note

- 守卫移除后不再有多次压缩兜底。若压缩后的结果仍然超出上下文上限，流程会再次进入 `compact`，由 token 计算这条路径决定。
- `keep_count` 的实际生效值在 `config.yaml`（已 gitignore，不入库），本版只同步模板默认值。

## Docs

- `plugins/context_compactor/README.md`：配置示例与配置表同步 `keep_count: 20`，新增各档位下「摘要 / 保留」权重对比表与风格漂移说明。
