# v0.41.0 - 2026-11-09

> 🧱 **一条消息带着自己的 `thread_id` 走进图，跑完原地回给它**。`thread_id` 从常量 `"main"` 变回消息自带的会话身份，执行锁从「全人类共用一把」拆成「一个会话一把」，通道协议收窄成 `to_text() -> str` + `reply(thread_id, text)`，唤醒从 `Job` 轮询换成 `tick` + `RUN_REQUESTED` 事件（破坏性）。

这一版没有新功能。它只是把 0.39.0 那版「通道化」欠下的账一次性还清 —— 还账路上又踩了三个新坑，其中一个差点让整张图一次都跑不起来（见 `Fixed` 第一条）。从 0.38.0 到今天共五天、八个提交、删掉一个 `api/` 模块、改两次协议、把 `thread_id` 从会话事实改成常量、再从常量改回会话事实 —— 全发生在同一个没打完的重构里，来回打转。

## 一颗 `"main"` 埋下的三颗雷

0.39.0 为了「让消息入口变成可插拔的通道」，把 `thread_id` 硬写成常量 `"main"`。当时看着很合理：入口都抽象掉了，图里当然只有一条会话。三颗雷就从这一行开始倒计时。

**第一颗：历史串台。** `checkpointer` 是按 `thread_id` 分区的，全部塞进 `"main"` 就等于把所有群、所有私聊灌进同一本日记。A 群的梗会被 B 群接着聊，压缩摘要里能读到隔壁的私房话 —— 不是「记忆强」，是没有墙。

**第二颗：锁变成收费站。** `INVOKE_LOCK` 全局唯一，谁跑图谁排队。两个毫不相干的人在同一秒说话，第二个必须等第一个把 LLM 请求、工具调用、压缩全套走完 —— 同一时刻只允许一个 `ainvoke` 活着。而端到端时延里「排队」本来就占了大部分（11-06 的服务器日志：排队中位 21.5s / p90 48.4s，占中位端到端时延 77%），再叠一层全局锁等于往伤口上撒盐。

**第三颗：回不去了。** 这一点最阴。`main.py` 手里只有一坨 `json.dumps` 拼出来的字符串，`thread_id` 是常量，`reply` 需要的东西一样都没有 —— 消息从入口被捏碎的那一刻，「这条话属于谁」的信息就永久丢失。等到要写回发的时候才发现：拼不回原样了。

三颗雷的共同点只有一条：**入口把身份捏碎了，下游就再也拼不回来。**

## 这一版怎么拆雷

`BaseChannelMessage` 补上 `thread_id` 与 `platform` 两个属性 —— 消息从出生就自带身份，一路不丢。`main.py` 拿到的每条消息都能回答「我属于谁」，于是：

- 跑图用 `message.thread_id`（会话墙回来了）
- 取锁用 `INVOKE_LOCKS[thread_id]`（收费站拆了，同会话串行、跨会话并发）
- 回复用 `channel.reply(message.thread_id, text)`（能回去了）

`INVOKE_LOCK` 这个单数名字必须死 —— 它已经不再是「一把锁」了，留着它就是在等下一次有人把全局锁写回来。改成 `INVOKE_LOCKS`，`api.get_invoke_lock()` 也跟着要求传 `thread_id`，不传就报错，报错比「悄悄拿到一把错的锁」好一万倍。

`reply` 挂在**渠道**上而不是消息上：消息是个无状态的入站记录，活不到能用的地方（`main.py` 拿到的已经是 `to_text()` 的字符串了）；渠道才有 client、有生命周期、有「怎么发」的知识。

## Added

- `models/config/tick_config.py`：`TickConfig`（`interval: float`，默认 `60.0`，`gt=0`），`PluginConfig` 多出 `tick` 段。
- `models/config/graph_config.py`：`GraphConfig`（`atimeout: float`，默认 `60.0`），`PluginConfig` 多出 `graph` 段 —— 单条消息跑图的总超时，和「拉取通道」的超时是两件事，混在一个键里迟早出事。
- `models/config/channel_config.py`：`ChannelConfig`，取代 `channel_setting.py` 的 `ChannelSetting`，字段 `drain_timeout` 改名 `atimeout`（默认 `30.0` 不变）。名字统一成 `atimeout` 是因为这两个超时都是 `wait_for` 的，叫 `timeout` 会让人以为是客户端自带的。
- `consts/share_store_keys.py`：新增 `RUN_REQUESTED`（`miaoli_bot/core.run_requested`），core 的容器键 11 → 12 个。
- `api/sync_ops.py`：新增 `please_run_graph()` —— 置位 `RUN_REQUESTED`，没有参数、没有返回值、不阻塞；连着调 N 次只对应一轮跑图。名字按四判据挑：不传数据、不返结果、不阻塞、**不一定跑**。`request` / `trigger` / `schedule` 都隐含「会被兑现」，而它本质上只是个标记。
- `api/sync_ops.py`：`get_invoke_lock()` 多出 `thread_id: str` 参数，返回该线程的锁。
- `protocols/channel/message.py`：新增抽象属性 `thread_id` 与 `platform` —— 前者是会话身份，后者是平台名（框架不解释它，只用来给渠道自己分流）。
- `protocols/channel/channel.py`：新增抽象方法 `reply(thread_id: str, text: str) -> None`。
- `main.py`：新增 `tick(tick_interval)` 常驻协程与 `_run_channel_graph(channel, message)` —— 前者负责唤醒与并发编排，后者负责「一条消息 → 一张图 → 一次回复」。

## Changed

- **破坏性**：`protocols/channel/message.py` 的 `ChannelMessage` 改名 `BaseChannelMessage`；`raw` 属性删除；`to_structured() -> Union[dict, list, str]` 改名 `to_text() -> str`。
- `protocols/`、`protocols/channel/`、`models/`、`consts/`、`api/` 的再导出与 `__all__` 全部跟着改名。
- `core/notice_channel/channel_surface.py`：`batch_drain()` 的返回类型从 `Dict[str, Union[ChannelMessage, Exception]]`（渠道名 → 消息**或异常**）变成 `Dict[BaseChannel, BaseChannelMessage]` —— 键直接放渠道实例，省掉一次按名字反查；值里也不再混 `Exception`（异常在 `_drain_c` 里打完日志就 `raise`，由 `gather(return_exceptions=True)` 收走，最后只留 `(渠道, 消息)` 元组）。
- `core/notice_channel/channel_registry.py`：`self._channels` 从 `Dict[str, BaseChannel]` 改成 `List[BaseChannel]`，唯一性判据是 `BaseChannel.name`；`to_surface()` 返回 `ChannelSurface(list(self._channels))` —— 每轮拿到的是副本，图里怎么折腾都碰不到注册表本体。
- `core/graph_runner.py`：`safe_run_graph()` 的锁从 `INVOKE_LOCK` 换成 `INVOKE_LOCKS[thread_id]`。
- `main.py`：唤醒从 `Job(self.run_graph, Every(timedelta(seconds=60)), job_id="auto_wake")` 换成 `tick(tick_interval)` 协程 —— 每轮 `await_for(RUN_REQUESTED.wait(), timeout=tick_interval)`（`TimeoutError` 就是兜底到点），醒来先 `clear()` 再拉取。`clear()` 必须在跑图**之前**：放在后面的话，跑图期间到达的请求会被一起抹掉，那批消息只能等下一次兜底超时。
- `main.py`：`run_graph()` 拆成 `tick()` + `_run_channel_graph()`。`tick` 只做「醒 → 拉 → 每条消息造一个带超时的协程 → `gather` 收异常」；`_run_channel_graph` 做「空消息直接跳过 → 用 `message.thread_id` 跑图 → 按结果分支 → `channel.reply`」。
- `main.py`：`plugin_loader` 的实例化、`prepare_plugins()` / `load_plugins()`、`tick` 任务的创建全部从 `on_load` 挪到 `on_startup`（`on_load` 只造容器数据），`MAIN_READY.set()` 落在最后一行。
- `main.py`：`tick` 任务带一个 `add_done_callback` —— 任务意外结束时打日志并重新创建，但只在 `MAIN_READY` 置位时重启；`on_close` 开头先 `clear()` 它，于是关闭期间的正常结束保持静默。
- `main.py`：`on_close` 的顺序改成「`clear(MAIN_READY)` → `cancel` + `await tick` → `unload_plugins()` → `cpa.close()` → drop 各键」。原顺序先卸插件，而循环此时可能正拿着这些插件注册的工具跑图。
- `models/config/llm_config.py`：`thinking` 改名 `thinking_effort`（破坏性）；`check_provider_and_model` 校验器里的报错文案跟着改。
- `models/config/plugin_config.py`：`PluginConfig` 从 4 段变 6 段 —— `llm` / `tick` / `graph` / `checkpointer` / `sub_plugin` / `channel`。
- `api/__init__.py`：`safe_run_graph` 改成从 `core` 直接转出，`please_run_graph` 加进 `sync_ops` 的导出；`__all__` 仍是 16 项（去掉 `get_pipeline`、加上 `please_run_graph`）。
- `config.example.yaml`：新增 `tick:` / `graph:` 段，`channel.drain_timeout` → `channel.atimeout`，`llm.thinking` → `llm.thinking_effort`。
- `plugins/miaoli_bot_adapter/data/output_protocol.md`：**整篇回滚到 0.37.0 的内容**。0.39.0 / 0.39.1 把它改写成「最终文本没人看得到，唯一路径是调用发送工具」，而现在的链路是 `channel.reply` 直接发末条 `AIMessage` —— 提示词把模型往工具上赶、代码又在等正文，两边各说各话。回滚后它重新是「普通文字直接写在回复正文里，系统会自动发送；工具只用于媒体 / @人 / 主动发起 / 发别的会话」。人格（`SOUL.md`）不回滚。

## Removed

- `api/pipeline_ops.py`：整个文件删除，`get_pipeline()` 随之消失（破坏性）。它返回裸 `GraphPipeline`，调用方拿到后自己 `ainvoke` 会绕过 `graph_runner` 里的锁 —— 两个 `ainvoke` 同时写同一个 `thread_id` 的 checkpoint，轻则丢历史、重则让 checkpointer 抛错。要跑图只剩两条路：`safe_run_graph()`（带数据、同步拿结果）与 `please_run_graph()`（不带数据、不拿结果、可能被跳过）。
- `models/graph_state.py`：删除 `raw_input` 字段（以及随之无用的 `UntrackedValue` 导入）。全仓库零读取 —— 它从 0.38.0 登场那天起就只是个写着好看的字段。
- `protocols/channel/message.py`：删除 `raw` 属性。它的语义是「原始数据」，但没有任何框架代码读它，留着只会诱使下游绕过 `to_text()` 去抠原始事件。
- `models/config/channel_setting.py`：文件删除，内容迁到 `channel_config.py`。

## Fixed

- 🔴 `core/graph_runner.py`：`pipeline.ainvoke(state=state, ...)` 调到的是 `GraphPipeline.ainvoke(input, thread_id, *, context)`，形参叫 `input` 不叫 `state` —— 每次跑图必抛 `TypeError: unexpected keyword argument 'state'`，被 `safe_run_graph` 的 `except Exception` 接住、变成一个 `Exception` 返回值，最后只在 `main.py` 打一行「跑图时出现异常」。**整条回复链路 100% 失灵，而日志看起来只是「有点吵」**。改成位置参数 `ainvoke(state, thread_id=thread_id, context=context)`。这个坑是「异常兜底把致命错误降级成日志」的教科书案例：兜底本身没错，错在没有让它响。
- `utils/sugar.py`：`easier_send` 的分支从 `if / else` 改成 `if / elif / else`，非法的 `mode` 不再静默当成私聊发送，改为抛 `ValueError`。

## Note

- **旧 `config.yaml` 会校验失败**：`llm.thinking` 必须改成 `llm.thinking_effort`；`channel.drain_timeout` 要改成 `atimeout`；`tick` / `graph` 两段可整段省略，用默认值。
- **一个渠道一次 `drain()` 只交一条消息**。这是协议刻意的形状：一条消息 = 一个回合，渠道可以在这一条里塞任意东西（纯文本、JSON、markdown、唤醒提示、一句话摘要）。代价是渠道里积压 N 条就要 N 轮 —— 渠道要么自己攒批成一条，要么在 `drain()` 之后发现还有货就再 `please_run_graph()` 一次。主包不替它决定。
- **`\n\n` 的切分责任在渠道**。输出协议里「两个换行 = 对方收到两条独立 QQ 消息」，而 `reply` 只拿得到一个 `text` 字符串。主包不切、也不该切。
- `core/scheduler/`（`Job` / `Once` / `Every`）仍在仓库里，但已经没有使用者 —— 唤醒改由 `main.py` 的 `tick` 任务负责。
- 重启回调只在任务**整轮退出**时触发。`tick` 内部把每条消息的异常都 `gather` 掉了，所以单条失败不会掀翻整轮。
- `tick.interval` 必须大于 0：0 会让 `wait_for` 立刻超时，退化成忙循环。
