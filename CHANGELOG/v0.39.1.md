# v0.39.1 - 2026-11-07

> 🧱 **卸载时补上漏丢的 `MAIN_READY`，输出协议按「闸门已经筛过」重写，人设补三条说法**。1.0.0 拆出通道之后，`on_close` 少收了这一个键，共享容器的泄露检查从此每次卸载都报一行。

`SHARE_STORE` 的约定是「`on_load` 放进来的，`on_close` 全部拿走」：`TOOL_REGISTRY` / `GRAPH_PIPELINE` / `HANDLER_REGISTRY` / `CHANNEL_REGISTRY` / `INVOKE_LOCK` 都带自己的 `drop`，唯独 `MAIN_READY`（`on_load` 里造的那个 `asyncio.Event`）没有。插件卸载之后容器非空，`is_empty()` 判否，那行「共享容器可能存在资源泄露」的告警每次都会打出来。

残留的还不是个中性对象：那是个已经 `set()` 的 Event，`wait_main_ready()` 拿到它不阻塞。所以落在「卸载之后、下一次 `on_load` 造新 Event 之前」里的调用方会被直接放行，而子插件其实还没装完。

另外两处提示词改动不是 bug 修复，只是同一个工作区里的改动一起走这一版。输出协议重写的动因在通道侧：`miaoli_qq_channel` 已经用「被 @」「被叫昵称」两条代码级硬闸门决定哪批消息进模型，而协议里那张「什么时候不发」的否决清单相当于对已经放行的批次二审 —— 模型要么过度沉默，要么在正文里把「这条算不算叫我」的辩论过程写出来。

## Fixed

- `main.py`：`on_close` 补 `SHARE_STORE.drop(MAIN_READY)`。此前卸载后 `miaoli_bot/core.main_ready` 留在共享容器里，`is_empty()` 判否时那行泄露告警每次卸载都会打；残留的 `asyncio.Event` 还是已 `set()` 的，「卸载之后、下一次 `on_load` 之前」的 `wait_main_ready()` 会立刻返回而不是等就绪。

## Note

- 新版输出协议按「能进模型的批次里一定有人叫过你」这个前提写。它成立的条件是通道侧只有硬闸门（`at_me` / `name_mentioned`）。等 `miaoli_qq_channel` 的软规则（返回 `AddScore` 的节点）上线、非 @ 的消息也能进模型，这条前提就不成立了，协议要同步补一句「这批进来的原因不一定是叫你」。
